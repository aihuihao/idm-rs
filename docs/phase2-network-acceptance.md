## 关于 B 为什么没有发生切分

这是协议在起作用，不是切分没有接入。证据：

1. 分块数 = 连接数 = 8，运行期间 `PROGRESS ... active_chunks=8`（A 的 756 条、
   B 的 350 条进度行里最大值都是 8，从未超过上限）。也就是说**没有空闲连接**，
   而切分只在"某个分块完成、连接空闲"时才尝试（`download.rs:604-626`）。
2. 第一次有连接空闲的时刻，其他分块剩下的数据量已经不足 2 × `min_split`（默认 1 MiB）：
   B 的分块耗时 741.85 s ~ 754.75 s，单连接吞吐约 132 KB/s，
   第一个分块完成时其余分块最多还剩 ≈(754.75-741.85) × 132 KB/s ≈ 1.7 MB。
   协议第 3 步要求 `split - reserved ≥ min_split` 且 `end - split ≥ min_split`，
   剩余 1.7 MB 连一半都不到 1 MiB，因此 `compute_split_point` 返回 `None`，切分被正确放弃
   （见 `split.rs:149-159`）。
3. 本轮两次运行的瓶颈都在链路上（A 达到 2.16 MiB/s、B 只有 1.00 MiB/s，都低于 3 MiB/s 的
   限速值），8 条连接被服务器/链路较均匀地分摊带宽，8 个等长分块几乎同时结束
   （B 的 8 个分块耗时相差 ≤ 1.8%），没有出现"某条连接明显落后"的落后者，
   工作窃取自然没有可窃取的对象。

因此本次真实网络验收的结论是：**开启切分没有引入任何回归（文件完整、哈希一致、
并发不超上限、无限速失效），但这条链路没有出现需要切分的落后者**。
切分真正生效的证据来自本地可控实验：第四部分第 4 项（第 0 号分块限速 2 MiB/s 时
1.46 s vs 2.61 s）、第 5 项（50 个随机种子 64 MiB）、第 11 项（20 轮崩溃恢复中每轮切分 2~3 次）。

## 与 Phase 1d 的对比

Phase 1d 在同一条链路上用 4 连接 / 1.5M 限速跑过两次（575.66 s 与 1265.22 s），
耗时差异同样来自链路波动。本次 A、B 的耗时差（349.66 s vs 755.21 s）**不能**解读为
"切分变慢"：两次运行的瓶颈都是链路（均未触及 3M 限速），且 B 运行时单连接吞吐
只有 A 的 46%。切分本身的收益需要在"存在明显落后者"的场景衡量，见上文引用到的
第 4、5、11 项实验。
