# 任务：idm-rs Phase 2.2.1 —— 接管的两处补全

2.2 报告中的偏差 1 到 6 全部认可，保持不变。

## 一、接管时切分点不对齐

现状：接管的切分点是 reserved 向上对齐到 64 KiB，原分块会保留不到 64 KiB 的尾巴。真实网络中数据按任意大小到达，reserved 几乎不会恰好对齐。原分块如果是卡住的，这截尾巴要等到 read_timeout（30 秒）才能继续。2.2 的停顿测试之所以通过，是因为测试服务器按 64 KiB 整块发送，reserved 恰好对齐。

修正：接管时 split = reserved，不对齐。对半切分仍然对齐到 64 KiB。

## 二、零进度分块的接管（延迟分配）

现状：接管要求 split > start（写入器的区间不能为空），所以一个字节都没收到就卡住的分块无法被接管。

修正：当被接管的分块 reserved == start 时：
1. 第 4 步：把 end 缩为 start（区间变为空），同时更新 watch，唤醒该分块
2. 第 5 步：数据库事务照常执行，split = start（被接管分块的记录变为 [start, start) 空区间，新分块为 [start, 原 end)）
3. 第 6 步：**不调用 shrink_end**
4. 第 7 步：**延迟执行**。在主循环中记录"待启动的新分块"，等被接管分块的任务以 Completed 结束（它会走到 release，释放写入器）之后，再为新分块 allocate_chunk、register、启动连接。被接管分块 5 秒内仍未结束，任务失败（属于程序错误）
5. 等待被接管分块结束的这段时间里，主循环照常处理其他事件，不得阻塞

同时补全唤醒点：**等待服务器返回响应头（`req.send()`）时，也要监听 end 的 watch**。被唤醒后如果 acked == end，丢弃这次请求，返回 Completed。

## 三、ARCHITECTURE.md 第 10.5 节修订

把 10.5 节中"切分点"一条改为：

```
- 切分点：split = reserved（不对齐）。要求 end − split ≥ 256 KiB，否则放弃本次切分
- 当 reserved == start（被接管分块尚未写入任何数据）时：end 缩为 start，不调用 shrink_end；新分块的写入器分配和网络请求，延迟到被接管分块的任务结束、释放写入器之后再执行
- 唤醒点包括：等待响应头、等待网络数据、重试退避等待
```

## 四、测试

1. 停顿测试改为"不对齐"：服务器让第 0 号分块先发送 **100000 字节**（不是 64 KiB 的整数倍，并且按大小不一的块发送，例如在 1 KiB 到 16 KiB 之间随机），然后停住 20 秒。断言：开启切分时 5 秒内完成；服务器记录到连接被提前关闭；逐字节正确
2. **零进度停顿**：服务器对第 0 号分块的请求接受连接后，20 秒内不返回任何响应头，也不关闭连接。断言：开启切分时 5 秒内完成；服务器记录到这个连接被客户端提前关闭；逐字节正确；数据库分块记录满足 10.4（空区间的记录允许存在）
3. 极慢测试（10 KiB/s）：报告修改后开启切分的耗时（预期明显低于 2.2 的 6 秒）
4. 单元测试：接管的切分点等于 reserved；reserved == start 时走延迟分配路径
