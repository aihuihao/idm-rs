# 任务：idm-rs Phase 2.2 —— 卡住与极慢分块的接管

沿用全部工作规则。先把本任务原文保存为 `docs/prompts/phase2.2.md`，`git status` 必须干净。

## 背景

现在的切分是对半分。被切分的分块如果完全卡住，它保留的前一半同样下不动，任务仍要等到 read_timeout 触发重试。2.1 的停顿测试是靠"测试服务器在新请求到达时放开卡住的连接"才通过的，真实服务器不会这样配合。本轮改为"接管"模式，并且让卡住的分块能被立刻唤醒、退出。

## 一、ARCHITECTURE.md 追加 10.5 节（原样写入）

```
### 10.5 接管模式（Phase 2.2）
- 触发条件：被选中的分块满足下列之一
  - 卡住：分块启动已超过一个速度窗口（4 秒），并且窗口内没有任何新数据
  - 明显慢：最近速度低于本任务所有正在下载、速度大于 0 的分块平均速度的 1/4
- 切分点：split = reserved 向上对齐到 64 KiB（reserved 已经对齐时，split = reserved）。要求 end − split ≥ 256 KiB，否则放弃本次切分
- 第 4 步的确认条件放宽为 reserved ≤ split（普通对半切分仍为 reserved < split）。不变式 committed ≤ acked ≤ reserved ≤ end 保持不变
- 唤醒：end 被缩小后，必须能唤醒正在等待网络数据或正在退避等待的分块任务。被唤醒的分块如果发现 acked == end，立即丢弃连接，以"完成"结束
- 第 5 到 7 步（数据库事务 → shrink_end → 新分块）不变
```

## 二、实现

1. **接管判断**：在 `select_victim` 选出分块后，按 10.5 判断是"接管"还是"对半切"，分别计算切分点。日志和汇总表中区分这两种方式
2. **唤醒机制**：ChunkShared 中增加一个 `tokio::sync::watch` 通道，镜像当前的 end（状态语义，不会漏掉通知）。`commit_split` 修改 end 时同步更新它。分块任务在以下两处的 `select!` 中同时监听它：
   - 等待网络数据（`resp.chunk()`）时
   - 重试退避等待时
   被唤醒后加锁检查：acked == end → 丢弃响应（关闭连接），返回 Completed；否则继续原来的等待
3. **剩余长度为 0 的保护（必须）**：每次尝试开始时，如果当前位置 ≥ end，直接返回 Completed，不得发送任何请求。删除 `expected == 0` 时发送 `bytes=0-0` 的分支。分块下载过程中，任何情况下都不允许发出起点等于终点的 Range 请求

## 三、测试

1. 单元测试：接管模式的切分点（向上对齐、已对齐时等于 reserved、剩余不足 256 KiB 时放弃）；`reserved == split` 时接管的确认能成功，对半切分的确认失败
2. 单元测试：唤醒——分块在等待时 end 被缩小到 acked，任务在 100 毫秒内返回 Completed
3. **重写 2.1 的停顿集成测试，去掉"新请求到达时放开卡住的连接"这个机制**：服务器让第 0 号分块发送一部分数据后停住 20 秒（小于 read_timeout 的 30 秒），停住期间绝不发送数据，也不主动关闭连接。断言：
   - 开启切分时，下载在 5 秒内完成，逐字节正确
   - 服务器端观察到第 0 号分块的连接在 20 秒到期之前就被客户端关闭了
   - `--no-split` 时耗时不少于 20 秒
4. 极慢分块：第 0 号分块限速 10 KiB/s，其他分块不限速。开启切分时触发接管，总耗时远短于 `--no-split`，并报告两者的实测耗时
5. 退避期间被接管：第 0 号分块中途断开并进入较长的退避等待（例如退避基数设为 10 秒），在此期间被接管到 acked。断言：该分块以 Completed 结束；测试服务器记录到的所有 Range 请求中，没有起点等于终点的请求；文件逐字节正确
6. 回归：第 4、5、11 项（phase2）以及全部原有测试、两个崩溃测试都通过
