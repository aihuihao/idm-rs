# 任务：idm-rs Phase 2.1 —— 切分修正

沿用全部工作规则。先把本任务原文保存为 `docs/prompts/phase2.1.md`，`git status` 必须干净。ARCHITECTURE 第 10 节的协议步骤不变。

## 一、续传时新分块编号冲突（必须修）

现状：`run_download` 中 `next_db_index` 只从 `inits`（committed < end 的分块）中取最大值加一。如果编号最大的分块已经完成，它被过滤掉了，新编号会与数据库中已有的分块编号重复，切分时插入数据库会因主键冲突而失败。

修正：续传时，`next_db_index` 取 `plan.chunks`（数据库中的全部分块记录）的最大编号加一。

测试：构造一个已暂停的任务，其中编号最大的分块（由切分产生）已经完成。resume 后触发至少一次切分，下载完成且逐字节正确，数据库分块记录满足 10.4 的不变式。

## 二、速度计算要能反映"卡住"（应该修）

现状：`recent_speed` 按"窗口内第一个和最后一个采样点"计算速度。连接卡住后不再产生采样，速度会一直停留在卡住前的值，不会降为 0。

修正：
- 速度 = (最后一个采样的位置 − 窗口起点的位置) / (**当前时间** − 窗口起点的时间)
- 窗口内（最近 4 秒）没有任何新采样时，速度为 0

测试（单元测试）：采样若干次后停止采样，等待超过窗口长度，`recent_speed` 返回 0。

## 三、选择被切分分块的规则（应该修）

修正 `select_victim`：
1. **先过滤再比较**：只在"按 compute_split_point 能切分成功"的分块中选择预计剩余时间最长的。不能切分的分块（剩余太少）不参与比较，不能因为它而放弃本次切分
2. **刚创建的分块不按速度 0 处理**：分块启动不满一个速度窗口（4 秒），并且还没有写入任何数据时，用本任务所有正在下载的分块的平均速度来估算它的剩余时间。如果所有分块都没有速度数据，就按无穷大处理
3. 启动超过 4 秒、但窗口内没有数据的分块（卡住或正在退避重试），速度为 0，预计剩余时间为无穷大，优先被切分（与规格一致）

测试（单元测试，直接构造 ChunkSlot 或 ChunkShared 的状态）：
- 一个剩余太小、速度为 0 的分块，加上一个剩余很大的慢分块 → 选中后者
- 一个刚创建、没有数据的分块，加上一个剩余时间更长的正常分块 → 选中后者
- 一个已经卡住超过 4 秒的分块，加上几个正常分块 → 选中卡住的那个

集成测试：服务器让第 0 号分块发送一部分数据后**完全停住**（不断开连接，时长小于 read_timeout，所以不会触发重试），其他分块正常。开启切分时，第 0 号分块被切分，下载完成时间远短于它停住的时长，最终文件逐字节正确。

## 四、初始分块启动循环中的错误路径

`run_download` 里初始分块启动循环中的 `spawner.open(&shared).await?`，出错时会直接返回，已经启动的分块任务会随着 JoinSet 被 drop 而强行中止，没有经过协作式排空。修正为：出错时先触发内部取消信号，再走与主循环相同的排空流程（等待最多 5 秒），然后返回错误。
